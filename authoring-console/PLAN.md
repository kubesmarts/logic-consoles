# Authoring Console implementation plan

**Planning draft · 2026-11-20** · [Milestones and exit gates](ROADMAP.md) · [UI design specification](DESIGN.md) · [Architecture and API decisions](adr/0001-authoring-console.md) · [Agent working agreement](AGENTS.md)

A platform administrator should be able to prepare a cluster once. An author arriving later should be able to select a namespace, publish an example to an existing runtime, run a specific version and inspect the resulting instance. A cluster admin can complete both journeys. An author with namespace permissions can use a platform someone else configured.

## First release journey

### 1. Connect and resume

Start the installed Node.js/TypeScript launcher. It serves the bundled React UI on loopback and opens the default browser. Confirm the preselected kubeconfig context and namespace, then choose **Connect**. This flow covers KIND, remote Kubernetes and OpenShift contexts. [Local KIND quick start](docs/connect-kind.md) · [Accepted launcher design](adr/0001-authoring-console.md#local-launcher-accepted)

Show the active cluster and namespace throughout the console. Discover the four operator APIs and the caller's capabilities. For an existing platform, discover or enter its workstation-reachable gateway URL. For a new platform, continue setup and test the gateway after reconciliation. Show separate connection results for Kubernetes and the gateway. If the gateway is unreachable, show its address with **Change address** and **Retry**. Keep Kubernetes-backed setup and publishing available. Distinguish API connectivity, installation evidence, controller readiness if observable, and gateway health. When APIs are missing, open the operator's release-matched installation instructions and offer **Check again**. When access is denied, show the missing capability and keep accessible workflows usable. A returning user lands on the existing estate and can skip completed setup. [Operator installation](https://github.com/kubesmarts/logic-operator/blob/b9a71660267f0cad794b95e010569b280a932da8/docs/antora/modules/ROOT/pages/deployment/install.adoc) · [Local KIND setup](https://github.com/kubesmarts/logic-operator/blob/b9a71660267f0cad794b95e010569b280a932da8/docs/antora/modules/ROOT/pages/deployment/kind-local.adoc)

Serve the same frontend build from a static host for direct browser access. For example, an author on a customer VPN opens the hosted UI and supplies an internal OpenShift API URL and short-lived token. The browser reaches the API and gateway Route over the customer network. Keep the manual instructions with that option. [Direct browser setup](docs/direct-browser-kind.md)

### 2. Create or edit the platform

1. Discover the singleton. Offer **Set up platform** if absent and permitted, or **View configuration** and **Edit** if present and permitted. If the user can read the platform but cannot edit it, show **Continue to workflows**. If platform discovery returns 403, keep namespace and runtime selection available. Select an existing target namespace or enter its name when listing is restricted. Offer **Create namespace** during platform creation when the caller can create core/v1 namespaces at cluster scope. Explain that the platform target becomes immutable after the platform is created.
2. Recommend **Run a workflow and see its history** and offer **Quick run without history** alongside it. Both run the example synchronously and display its output. The quick path uses a gateway and an ephemeral runtime. Durable execution is a separate choice.
3. For history, configure the Data Index PostgreSQL Secret name, Service name/namespace, database and schema. Offer the maintained PostgreSQL deployment example with its required Secret keys and schemas. The user installs it independently and returns to the wizard. Collect references only. A user who cannot list Secrets can type the name.
4. Configure Vector with Data Index enabled and one watched runtime namespace for this baseline. Explain the runtime's structured logging dependency. For durable execution configure the runtime and Quartz stores separately. Keep sensitive payload logging opt-in.
5. Configure the shared gateway endpoint. On Kubernetes and KIND the first release uses an installed community `ingress-nginx` controller with class `nginx` in the sample. Gateway API support follows the operator roadmap. Enable gateway ingress and set the host and matching ingress class. Where readable, show the IngressClass and Ingress status. Test gateway reachability through the active connection. If the prerequisite is missing, link cluster setup guidance. On OpenShift use the gateway Route. Publishing a workflow keeps its runtime internal. LogicFlowService has no first-release wizard. Review the complete CR in YAML, dry-run, submit and report readiness for each enabled component. When readiness stalls, show the operator's reason and message with the affected resource.

[Platform reference](https://github.com/kubesmarts/logic-operator/blob/b9a71660267f0cad794b95e010569b280a932da8/docs/antora/modules/ROOT/pages/crd-reference/clusterlogicplatform.adoc) · [PostgreSQL example](https://github.com/kubesmarts/logic-operator/blob/b9a71660267f0cad794b95e010569b280a932da8/config/samples/persistence/postgresql.yaml) · [History prerequisites](https://github.com/kubesmarts/logic-operator/blob/b9a71660267f0cad794b95e010569b280a932da8/docs/antora/modules/ROOT/pages/concepts/workflow-instance-history.adoc)

**Create namespace** opens a separate form with an editable YAML review of a core/v1 Namespace. A name is sufficient for the operator sample. Leave site-specific labels and annotations editable for cluster admission policies. Dry-run and submit the Namespace with the caller’s credentials. On success, select its returned name and resume the platform draft. If the name already exists, offer to select that namespace after checking its status when readable. Do not overwrite it. Treat a forbidden lookup as unknown. If an administrator must provision the namespace separately, offer a copyable `kubectl create namespace <name>` command and **Check again**. The wizard creates no role bindings. A later platform failure or cancellation leaves the namespace in place for reuse.

**Concurrent platform setup.** If dry-run or create reports an existing object or singleton admission conflict, preserve the create draft and rediscover the cluster-scoped platform. When readable, offer **View existing platform**. Opening it is a read. For a stale edit, fetch the current platform, compare it with the retained draft, and let the admin reapply their intended changes. Repeat dry-run using the refreshed resourceVersion and require explicit submission.

### 3. Create or reuse a runtime

Offer an existing same-namespace runtime or guide the user through name, namespace, platform reference, Ephemeral or PlatformDB persistence, replicas, structured logging and runner security. Show the additional datastore or Secret references required by the selected configuration. Keep advanced pod configuration in the full CR editor. Show ready replicas, conditions and definitions as they become available. Warn when the runtime will run outside Vector's watched namespace. A restricted author can select a runtime without permission to create one.

### 4. Author a workflow

Open a blank YAML editor with completion, hover help and validation against the release's DSL schema. Offer **Start from example** as a separate entry. Build the catalog from a pinned upstream revision, retain license and source links, and label examples with external service or credential prerequisites. Test at least one self-contained example end to end. Copying an example produces an independent, editable draft. Load the catalog with the app so GitHub availability cannot interrupt authoring. [Official specification examples](https://github.com/open-workflow-specification/specification/tree/main/examples)

The author edits the portable workflow document. Show the embedded CNCF diagram beside it or in a tab on narrow screens. Invalid intermediate YAML must stay editable and visibly invalidate the preview. Offer a snippet for a workflow-level inline input schema and explain its effect on the Run form. The full Kubernetes CR becomes available at publish review. A change to `spec.flow` during review feeds back into the same workflow draft. Offer YAML export and protect unsaved work on navigation. Use browser localStorage for console-owned state. The proposed first cut gives authors **Save draft on this device**, resume and remove. Verify that a draft survives a launcher restart and reload in the same browser profile on the same origin and that a storage error preserves the working copy for export.

### 5. Publish and update

Choose cluster, namespace and exactly one runtime. Resolve the workflow by namespace/document name, then by version. First publication lists eligible runtimes in the selected namespace. Subsequent versions use the family's established runtime. Show the effective document namespace before publish. If selection conflicts with an existing family, show its runtime and link to it. A raw YAML edit goes through the same checks.

When editing a published workflow, default to **Publish new version** and suggest an available version. Create a distinct CR on this path. **Update existing version** requires explicit selection. If the suggested version was taken concurrently, retain the draft and offer a different version. Generate the CR name from the version suffix and the remaining workflow-name budget. [Version and naming rules](adr/0001-authoring-console.md#suggested-versions-and-generated-cr-names) Group deployed versions from the gateway catalog by its namespace and workflow name. To open the Kubernetes CR for a selected version, use the gateway reader’s lookup convention. Scope the list to the Kubernetes namespace, match the workflow-name and workflow-version labels, then fetch the object by its returned metadata.name. This also resolves hand-authored CR names. On an in-place update, show the deployed-to-draft diff and concurrency check. If two authors race, retain the draft, refetch and explain admission or conflict results. Surface ambiguity when multiple CRs already claim a workflow version. Treat the operator as the authority. Show **Submitted**, then readiness and gateway discovery, so authors know when **Run this version** becomes available.

### 6. Inspect and run

Open a scoped topology using gateway nodes, edges, warnings and readiness. Provide an equivalent keyboard-accessible list. Keep resource name and workflow identity separate when linking a definition node to its workflow, version, runtime and history. A partial graph keeps its available nodes and explains missing sources. A 503 from topology has its own retry state.

On a definition version, show diagram, YAML, **Run** and **Instance history**. Build Run fields from workflow-level `input.schema.document` for supported JSON Schema objects, required properties, primitive fields, nested objects, arrays and enums. Validate with the supported dialect and offer JSON input for advanced shapes or absent schemas. For external `input.schema.resource` or unsupported dialects, explain the limitation and offer raw JSON without claiming schema validation. Never fetch arbitrary references using cluster credentials. Confirm runner and gateway body support before allowing non-object root inputs. [DSL schema](https://github.com/open-workflow-specification/specification/blob/main/schema/workflow.yaml)

Offer **Run and wait** and **Start in background** with the selected version visible. Use only the selected version’s advertised execution link for that mode. If the link is missing, points at another version or omits the version, keep the input and explain that execution is unavailable. For the onboarding example, select **Run and wait** and display the returned workflow output immediately. On async acceptance show the instance ID immediately. Offer history when the gateway can query Data Index. Show configuration guidance when it is disabled and a retry state for a configured but unavailable index. Preserve the sync output or async receipt in either case. A newly accepted instance may take time to appear. Distinguish empty history, pending indexing, unavailable Data Index (503 can also mean discovery is pending), upstream error (502) and denied access. After a start request times out, retain the input and report that the workflow may have started. With Data Index disabled, explain that history is unavailable and label an explicit second submission **Start another run**. With working Data Index, offer instance detail if the ID is known, otherwise offer history filtered to the selected workflow version. Recent rows and empty results cannot establish the outcome of an unidentified request. If a configured index is temporarily unreachable, offer **Retry history**. Never automatically repeat an execution POST. History filters use the actual namespace, workflow name, version and optional status. Open detail by ID through the gateway. In this release the gateway uses its service account for discovery. History reflects what its Data Index connection can return. User-scoped enforcement belongs to the later authenticated gateway release.

### Instance actions in M5

From a selected instance, authors can **Suspend**, **Resume** and **Cancel instance**. Use the selected definition version’s advertised operation link, substitute the encoded instance ID and POST once. The runner decides whether the caller may act and whether the current state allows the transition. Indexed history may lag. Show the operation result immediately, refresh the instance detail when available and distinguish a stale-state rejection or unknown outcome from a completed transition. Confirm cancellation with the target instance visible. [Gateway links](https://github.com/kubesmarts/logic-operator/blob/b9a71660267f0cad794b95e010569b280a932da8/workflow-gateway/internal/server/server.go#L149-L160)

## Parallel implementation

Proposed ownership paths below are relative to `authoring-console/`. They describe future work. The first live gate publishes a second workflow version and runs it synchronously on the stock KIND demo. A separate history-enabled KIND profile verifies indexing at M5. Use the roadmap to track when each packet’s work integrates.

| Packet and ownership | Inputs and handoff | Acceptance evidence |
| --- | --- | --- |
| A · Shell and fixtures · `src/app/`, `src/contracts/`, workspace config | Start first. Pin dependencies and release inputs. Publish session identity, resource and workflow keys, capability/error types, Kubernetes read/dry-run/write/status and gateway read/run interfaces, plus mock handlers. Own navigation, dependency changes and the localStorage interface. | Shell hosts PatternFly and both editors. Every consumer can run against the same fixtures for allowed, forbidden, loading and unavailable states. |
| B · Local launcher and connection · `launcher/`, `src/connection/` | Use A’s transport contracts. Own the Node.js/TypeScript entry point, bundled asset serving, loopback session, context selection, discovery, gateway calls and disconnect. Support the wizard’s separate namespace create capability, dry-run and submit in both connection adapters. Keep direct URL/token access a separate adapter. | Starting the launcher on the stock KIND demo opens the UI. Select the existing context, dry-run a permitted write and run hello-world synchronously through ingress-nginx using existing cluster configuration. Repeat with a remote context, reduced rights and an unreachable gateway. Context changes invalidate pending writes. |
| C · CR editing · `src/resource-editor/` | A supplies Kubernetes transport. Deliver form path updates, YAML, dry-run, diff, write and reconciliation interfaces to D and E. | A user edits a valid advanced pod field, toggles both ways and applies identical intent. Invalid YAML, stale writes and admission errors preserve the draft. |
| D · Platform and runtime · `src/setup/` | Build wizard screens on A fixtures and C's editor contract. Consume B for live data. | New and pre-existing platform paths work. Gateway-only and history-enabled configurations reconcile. An author denied platform updates can reuse a runtime and continue to publish. |
| E · Authoring and publish · `src/authoring/` | Use A's keys, pinned examples, C's review and D's runtime selection data. Expose a deployed version key after publish. | A blank document and an example both render and publish. Default publication creates a second version on the same runtime and preserves the first. Only the explicit update path mutates the selected CR. Advanced YAML changes and conflicts have coverage. |
| F · Shared operational views · `src/shared/operations/` | A supplies typed gateway fixtures and host-injected transport/navigation. Export topology, definition selection and history/detail views. | Version selection issues the correct filtered history request. Partial topology, empty history, index outage and delayed ingestion are distinguishable. Read views work in a minimal second host. |
| G · Run · `src/execution/` | Receive deployed version and workflow document from E/F. Use A's version-specific links. Supply Run and instance lifecycle actions from the authoring shell. F provides the selected instance ID and version to G. | Schema form and raw JSON send the same body. Sync output and async receipt are visible with Data Index disabled. With indexing enabled the user can also open history. A timeout produces exactly one POST. Suspend, resume and confirmed cancel target the same instance. |
| H · Compatibility and release · `src/compatibility/`, release manifest and integration suite | In M1, map each component to its tested version, available observation source and required read permissions. Own matrix, upstream drift review, tagged fixtures and final environment checks. | Page shows tested and detected versions with provenance. Complete the release evidence below. |

**Dispatch order.** A starts with the bundled frontend check in M1 while B and H can work on the launcher and operator contracts. A publishes the initial interfaces and fixture examples in one small change. C, D, E, F, G and H can then build against mocks while B proves the live connection. D and E integrate C before enabling writes. F and G integrate through a selected definition key and links. One integrator owns app routes, lockfile and the first live vertical slice. Each packet can be assigned using its row, the ADR and the agent agreement.

## Compatibility and release evidence

The compatibility page lists console version, operator release and API group/version, gateway version and API, Quarkus Flow and runner image/variant, Data Index, Vector, tested PostgreSQL, OWS DSL/editor, and tested KIND/Kubernetes/OpenShift versions. Include the tested NGINX controller implementation, version and ingress class for Kubernetes and KIND. For each component show tested values, detected image/version if readable, source and any override or unknown. For containerized components, show the observed image and its Kubernetes source. Match a running pod’s image digest to a known release digest before marking its version verified. With only a tag, display the tag as observed. For an unrecognized digest, display it and leave the version unverified. When RBAC prevents inspection, show **Unknown · insufficient access** and keep authoring available. Release 1 can ship this page with existing operator APIs. Record image digests where available.

Planning evidence from the inspected checkout is operator and gateway build defaults `2.0.0-Alpha4`, runner `1.3.0`, Data Index `2.0.0-SNAPSHOT-postgresql` and Vector `0.54.0-distroless-libc`. These are development inputs. No console compatibility row has been certified. [Build versions](https://github.com/kubesmarts/logic-operator/blob/b9a71660267f0cad794b95e010569b280a932da8/versions.mk) · [Vector version](https://github.com/kubesmarts/logic-operator/blob/b9a71660267f0cad794b95e010569b280a932da8/api/version/version.go)

1. After an operator release, select its tag and resolved images. Diff CRD schemas, admission behavior, gateway OpenAPI and runner fixtures against the prior supported set. Record the applicable DSL, editor and catalog revisions.
2. Install and start the packaged launcher. Run contract tests and a browser journey through its local API on clean KIND for missing operator guidance, platform, runtime, example, second version, both execution modes and indexed history. Repeat with an existing platform, reduced rights, disabled history and a stale edit. Verify publishing and both run modes on a fresh cluster with zero per-workflow LogicFlowService or ingress resources. Exercise a missing gateway ingress as its own setup state.
3. Verify remote Kubernetes connectivity and run a remote OpenShift smoke test with the intended identity and gateway exposure. Record exact versions and results. Exercise both a cluster admin and an author denied platform writes. Verify the author can publish a permitted definition, run it through the gateway and open history. Verify forbidden CR writes return 403 and gateway views reflect the gateway's access. Test runner rejection separately when invocation credentials are required.
4. Publish the tested matrix entry, compatibility page and console artifact after the operator release. For an unknown installation, show what was observed and which actions are verified. Keep portable authoring and export usable.
